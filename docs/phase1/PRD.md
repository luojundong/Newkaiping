## 0. 一句话产品定位

**开平市中心医院能源管理软件平台**是一套以 1:1 三维数字孪生为底、覆盖全院 10 栋楼 7 大能源子系统的"监、管、控"一体化平台——用一套可联动楼栋与子系统的可视化大屏，把分散的空调、照明、电力、热水、电梯等能耗与设备数据汇成唯一可信坐标系，并支持下发控制指令与生成碳排/能源自审报告，直接服务于医院节能降耗、安全运维与双碳考核。

## 1. 产品定位与核心价值

| 维度 | 说明 |
|------|------|
| 产品类型 | 行业垂直型（医疗）能源管理 + 数字孪生可视化平台（B 端、私有化部署） |
| 部署形态 | 本地/私有化服务器部署，内网运行（合同要求内网/外网分开） |
| 核心载体 | 数据大屏（指挥中心）+ 功能操作后台 + 设备详情 + 分级权限子界面 |
| 差异化一句话 | 不是"只监不控"的报表工具，也不是绑定硬件厂商的封闭 BMS，而是一套以国产可扩展技术栈、模型驱动、混合数据（模拟→真实可切换）、100% 控制闭环的本土化医院能源中台。 |

### 价值主张（对应合同与痛点）
1. **破数据孤岛**：将 7 个子系统与 10 栋楼数据汇入统一平台，打破后勤/设备科/基建各自为政的现状（调研痛点 1）。
2. **监、管、控一体**：合同明确要求"全量控制"——不仅展示，更能下发开关、温度、模式、策略组等指令并回传状态（直击"只监不控"痛点）。
3. **模型即导航**：3D 模型 + 顶部菜单双联动（楼栋 × 子系统），点击设备点位即聚焦、即查看、即控制（解决"粗放分析/找不到病灶"痛点）。
4. **可演进、不绑定厂商**：架构支持模拟数据先行、真实接口（MQTT/Modbus/HTTP 等）随时热切换的混合模式（ADR-003），避免外资平台"按点位持续授权、定制周期漫长"的短板。
5. **合规可考核**：用能统计/单耗分析/碳排分析/能源自审报告自动生成，适配绿色医院与双碳考核（回应"有标准难考核"痛点）。

## 2. 目标用户与用户画像

### 2.1 主要用户画像
- **画像 A：医院后勤/能源管理负责人（院级管理者）**
  - 角色：平台主用者，关注全院能耗总费用、碳排、科室定额考核、节能成效。
  - 技术水准：中等，习惯看大屏与报表，不关心底层协议。
  - 核心诉求：一个屏幕看清全院态势；能按科室/楼栋考核；能导出能源自审报告用于托管结算与考核。
- **画像 B：运维工程师 / 设备科技术员**
  - 角色：日常巡检、告警处理、设备控制、维保执行。
  - 技术水准：较高，熟悉空调/配电/楼控基本概念。
  - 核心诉求：在 3D 模型里点开设备看实时参数；远程开关空调/照明；收到告警后快速定位并确认/清除；查看设备台账与维修记录。
- **画像 C：院领导 / 参观接待（总览观众）**
  - 角色：occasionally 看大屏总览，关注整体节能成效与形象。
  - 核心诉求：大屏美观、信息密度高、关键指标一眼可见。

### 2.2 次要用户画像
- **画像 D：财务/绩效核算人员**：需要分科室、分楼栋的能耗账单用于成本核算。
- **画像 E：乙方实施/运维人员（珠海奥尼）**：需要后台配置菜单、标题、主题、设备接入、权限移交；质保期内的调试与排障。
- **画像 F：硬件/网关对接方（甲方自采设备厂商）**：通过标准协议把设备数据接入平台。

## 3. 核心问题与痛点（来自调研 + 合同）

| 编号 | 问题 | 现状（调研佐证） | 本项目如何解 |
|------|------|------------------|--------------|
| P1 | 数据孤岛 | 后勤、设备科、基建系统各自为政，无法多维联动分析（帆软/CHIMA/人人文档） | 7 子系统 + 10 楼统一平台，统一数据模型（buildings×subsystems×devices） |
| P2 | 只监不控 | 多数医院能源监控停留在"监测"非"管理"，不能下发指令（2026 医疗能源管理设备监控创新报告） | 合同全量控制要求，控制指令闭环 |
| P3 | 计量失真/系统废弃 | 电表参数错、流量计装错、系统长期无维护变"空壳"（CN-Healthcare/搜狐） | 数据校核 + 模型同步 + 操作日志全留痕 + 验收硬指标 |
| P4 | 分析粗放 | 只做到月/科室统计，无法到设备/房间/时段（帆软） | 设备级、楼层级、房间级钻取（?building_id= 驱动） |
| P5 | 误报警疲劳 | 固定阈值不适应医院峰谷，频繁误报致麻木（人人文档） | 可定制阈值 + 分级告警 + 告警确认/屏蔽 |
| P6 | 外资本土化弱 | 缺国内能耗平台接口、绿建需二次开发、按点位持续授权、培训周期长（搜狐/工控网） | 国产可扩展栈、本土化、私有化、无点位授权 |
| P7 | 平台聚合"灵活悖论" | 功能越聚合灵活性越受限（安庆公节） | 模块化子系统注册（7 独立 API 模块）、配置驱动、后台可扩 |
| P8 | 医疗特殊性 | 谐波/电能质量敏感、科室用能规律各异、根因分析弱（人人文档） | 电力监控含电能质量；按楼栋/科室维度分析 |

### 4.3 市场空白与本项目差异化
1. **管控一体 + 模型导航**：竞品多在"监测/合规"或"重托管运营"两端，少有"私有化买断 + 100%控制闭环 + 1:1 模型点选导航"的组合。
2. **混合数据、不绑定厂商**：模拟数据先行、真实接口热切换（ADR-003），规避外资"按点位授权/定制漫长"。
3. **10 栋楼 × 7 子系统统一联动**：填补美控类"跨楼栋联动偏少"的空白。
4. **验收硬指标驱动可信数据**：以控制延迟、模型同步延迟、日志全留痕对抗"假数据/空报表/系统废弃"。
5. **本土化交付**：广东本地项目、源码与权限全移交、质保 24 个月，规避外资本土化短板。

## 5. 导航模型（关键 UX 需求：楼栋 × 子系统双联动）

顶部菜单需**同时联动楼栋与子系统**，这是本项目相对参考工程（参考工程仅子系统导航）的核心差异。

- **一级：楼栋切换**（1–10 号楼），承载该院建筑功能：
  1 号 120 急救中心(急诊科)｜2 号 门诊大楼｜3 号 住院大楼｜4 号 妇产儿科大楼｜5 号 张襯大楼｜6 号 后勤楼｜7 号 药剂楼｜8 号 余锦炯大楼/放疗楼｜9 号 综合大楼｜10 号 宿舍楼
- **二级：子系统切换**（7 个）：
  智慧能源一体化调控平台｜设备生命周期管理系统｜空调集中控制调度系统｜智慧照明管理系统｜医院电力监控系统｜热水集中控制调度系统｜电梯节能管理系统
- **全局总览**：不锁定楼栋/子系统时的"全院一张图"。
- **联动规则**：切换楼栋 → 3D 模型定位到该楼、左右面板与设备详情刷新为该楼数据（对应 API `?building_id=` 过滤）；切换子系统 → 面板与模型高亮切换到该子系统视角（对应 7 个 API 模块之一）；两者正交组合，状态由全局导航 store 维护，大屏/后台/设备详情共享。

### 5.1 数据模型（对齐 ARCHITECTURE.md §7）

采用 **buildings × subsystems × devices** 三维归属模型：
- 任意数据/控制对象可唯一定位到三元组 `(building_id, subsystem, device_id)`。
- 楼栋（10）× 子系统（7）× 设备（台账），设备台账已可落成 `devices` 初始数据（见 §6 基线）。
- **1 号楼（120 急救中心）无设备数量台账**，标注"待台账"，架构已预留 `building_id=1` 设备维度，待甲方现场调研补充后解锁设备级功能。
- 该模型直接支撑顶部双联动：选 `building_id` 即过滤该楼全子系统数据；选 `subsystem` 即过滤该子系统跨楼数据。

### 5.2 API 契约映射（对齐 openapi.yaml / ARCHITECTURE.md §9）

**openapi.yaml 是前后端联调唯一契约**；PRD 功能清单、字段、错误码须与该契约一致，变更须同步更新 openapi.yaml 与本文档。

- **7 子系统 → 7 个 API 模块**，每个模块均以 `?building_id=` 出该楼数据：

| 子系统（PRD） | API 模块 | 对应功能点 |
|---------------|----------|------------|
| 智慧能源一体化调控平台 | `/regulation` | M1, M2, M3, M4 |
| 设备生命周期管理系统 | `/lifecycle` | M5, M6, M7 |
| 空调集中控制调度系统 | `/hvac` | M8, M9, M10, M11 |
| 智慧照明管理系统 | `/lighting` | M12, M13 |
| 医院电力监控系统 | `/power` | M14, M15, M16 |
| 热水集中控制调度系统 | `/hotwater` | M17 |
| 电梯节能管理系统 | `/elevator` | M18 |

- **跨域接口**（不绑定单一子系统，支撑总览/跨楼联动/告警）：
  - `/buildings`：楼栋元数据
  - `/devices`：设备台账与点位
  - `/metrics`：时序指标
  - `/energy`：能耗统计/单耗/碳排
  - `/alarms`：告警（支撑 M19/M20/M21/M22）
- **实时通道**：WebSocket `/api/v1/ws/live`，承载实时指标推送、设备状态回传、告警事件（对应 M20/M21/M22 实时部分与 §10 混合数据层）。
- **契约治理**：任一端（前端/后端/PRD）对字段、错误码、端点的变更，必须先更新 openapi.yaml 并同步回本文档，禁止单边漂移。

## 6. MVP 功能范围（按 7 个子系统拆解）

> **MVP 定义说明（重要）**：本项目的 7 个子系统为合同强制验收范围，**不做"砍功能"式 MVP**。但为降低交付风险、尽快形成可演示闭环，将 **Phase 1 MVP（首版可演示验收闭环）** 聚焦在"3 个最高价值锚点 + 全局骨架 + 验收硬性控制项"；其余子系统模块按 RICE 分批纳入（见第 8 节），全部属承诺范围，不删减。
>
> **3 个 MVP 锚点功能**：① 双联动导航 + 大屏集成骨架；② 智慧能源一体化调控平台总览；③ 设备生命周期管理基础台账。

### 6.1 智慧能源一体化调控平台（子系统 1，总览/头条 → /regulation）
- M1 全院一张图总览：全景图、设备运行、用能情况、能源分析、碳排分析、用能趋势"一个屏幕"监控。
- M2 电耗/空调/热水/电梯储能回馈/照明/配电间电能 全面统计分析与态势可视化。
- M3 用能统计、用能分析、单耗分析、碳排分析、能源自审报告自动生成（为托管结算/考核提供依据）。
- M4 各子系统（空调/热水/电梯/电力/照明）统一展示与集中入口。

### 6.2 设备生命周期管理系统（子系统 2 → /lifecycle）
- M5 用能设备档案管理：技术性能参数、生产时间、启用时间、数量、使用场地归属、生产厂家。
- M6 设备运行数据：工作时间、故障次数、维修记录。
- M7 维护保养：维修记录、保养计划、维护费用。

### 6.3 空调集中控制调度系统（子系统 3 → /hvac）
- M8 基于建筑/部门维度的楼栋·楼层·房间集中控制：开关状态、设定温度、运转模式、节能命令、遥控开关。
- M9 每台空调运行电流/功率/时间/电量统计；楼内每层空调总体状况与能耗汇总。
- M10 空调类型/品牌/类别/内机参数（开关、模式、设定温度、累计用电量）监测。
- M11 策略组：制冷下限、制热上限、开关机时间等，多策略组合绑定内机。

### 6.4 智慧照明管理系统（子系统 4 → /lighting）
- M12 基于建筑/部门维度的区域照明集中控制：联动控制、定时操控、远程操控。
- M13 楼栋照明能耗统计；特定场地智能感应控制。

### 6.5 医院电力监控系统（子系统 5 → /power）
- M14 单个电表每日用电量统计。
- M15 某时段内某区域/组织的用电明细查询。
- M16 某区域按能耗性质的年/月统计。

### 6.6 热水集中控制调度系统（子系统 6 → /hotwater）
- M17 热水设备数据接口对接、集中控制调度及数据呈现。

### 6.7 电梯节能管理系统（子系统 7 → /elevator）

## 7. 明确不做（Out-of-Scope）

- **不做硬件采购与现场施工**：合同 2.4.8 明确所有子系统硬件部署及采购由甲方自行完成，乙方仅免费配合适配调试。
- **不做消防/安防（FAS/SAS）核心系统**：本期聚焦能源 7 子系统；消防报警、视频监控、门禁不在范围内（仅在 3D 模型中预留点位扩展位）。
- **不做 AI 全局优化算法自研（本期）**：M11 策略组与阈值告警先做规则引擎；负荷预测/强化学习节能算法列入 Phase 3 候选，不在 MVP。
- **不做多院区/云 SaaS 多租户**：本期为单院私有化部署，架构预留扩展但不实现多租户。
- **不做移动端原生 App（本期）**：优先大屏 + Web 后台；移动端 H5/响应式作为 Phase 2 候选。
- **不绑定任何硬件厂商私有协议**：仅通过 MQTT/Modbus/HTTP/BACnet 等标准协议对接，避免厂商锁定。
- **不做医疗业务系统（HIS/LIS/PACS）对接**：仅能源相关数据，不触碰诊疗业务。

## 9. 用例 / 用户故事

- **US-1（后勤负责人 · 总览）**：作为后勤负责人，我希望在总览大屏一眼看到全院实时能耗、碳排与异常告警，以便向院领导汇报节能成效。Given 已登录且有权限，When 进入"智慧能源一体化调控平台"总览（/regulation + /energy），Then 左侧显示全院能耗趋势、右侧显示碳排与单耗、3D 模型高亮异常楼栋。
- **US-2（运维工程师 · 点选控制）**：作为运维工程师，我希望在 3D 模型点击 2 号楼某台分体机，查看实时电流/功率并远程关机，以便快速处置空耗。Given 选中设备点位（building_id=2, device_id），When 点击"遥控开关"（/hvac + WS 指令），Then 指令下发、状态回传、操作记入日志。
- **US-3（楼栋×子系统联动）**：作为任何用户，我希望在顶部先选"3 号楼"再选"空调集中控制"，以便只关注住院大楼空调。Given 已选 building_id=3 与 subsystem=hvac，When 切换其中任一项，Then 大屏、面板、设备详情全部按 `?building_id=3` 联动刷新。
- **US-4（告警处理）**：作为运维工程师，我希望收到空调超温告警后确认并屏蔽测试误报，以便减少告警疲劳。Given 存在未确认告警（/alarms + WS 推送），When 点击确认/屏蔽，Then 告警状态变更、声音停止、记录留存。
- **US-5（设备科 · 台账）**：作为设备科人员，我希望在设备生命周期系统查到某热水机组的出厂日期、维修记录与保养计划，以便安排维保。Given 进入设备档案（/lifecycle），When 搜索设备编号，Then 返回台账、运行数据、维保全链路。
- **US-6（财务 · 核算）**：作为财务人员，我希望按科室/楼栋导出月度能耗账单，以便成本核算。Given 进入电力监控/用能分析（/power、/energy），When 选择区域与时段并导出，Then 生成合规报表文件。
- **US-7（实施方 · 后台配置）**：作为乙方实施，我希望在后台配置菜单、标题、主题、设备接入协议，以便交付可配置平台。Given 拥有超级管理员权限，When 修改配置，Then 大屏准实时生效（参考工程 15s 轮询）。
- **US-8（权限隔离）**：作为低权限访客，我希望只能查看不能控制，以便防止误操作。Given 低权限账号，When 尝试下发控制指令，Then 指令被拦截并提示无权限。

## 10. 数据架构约束（混合模式，对齐 ADR-003，供架构师）

- **统一 DataSource 抽象**：数据接入层抽象为统一接口，提供 Mock / MQTT / Modbus / HTTP 适配器，由环境/配置驱动热切换，业务代码不感知数据来源。对应 PRD M25。
- **ADR-003 模拟/真实切换**：混合数据层以 ADR-003 为准——Mock 适配器与真实适配器（MQTT 主题、Modbus 寄存器表、HTTP 轮询）通过配置切换；任一子系统/设备可单独切真实协议，无需改动渲染与业务层。
- **先用模拟数据**：Phase 1 全量使用模拟数据（基于设备台账生成合理时序，含 1 号楼楼级占位），保证前端可独立开发。
- **存储**：关系型（设备台账/权限/日志）+ 时序数据库（设备时序/能耗），参考合同"高性能关系型+时序数据库组合"。
- **同步时效**：常规数据实时（WS `/api/v1/ws/live`），关键设备毫秒级（合同留空待填，目标 ≤ 设定阈值）；数据加密传输与存储。
- **API 边界**：前端仅通过 openapi.yaml 定义的 7 模块 + 跨域接口 + WS 通道取数/控设备，禁止直连数据库或私接协议；字段与错误码以 openapi.yaml 为唯一契约。

## 11. 非功能需求与验收标准

| 类别 | 要求 | 优先级 | 合同依据 |
|------|------|--------|----------|

| 模型同步 | 虚拟模型与物理实体位置/状态/参数实时同步，延迟符合行业（待填） | P0 | 系统核心功能标准 |
| 安全 | 分级角色权限、操作日志全留痕、数据加密传输与存储、防篡改防泄露 | P0 | 安全权限管理 |
| 可扩展 | 支持功能迭代、设备新增、场景扩容、接口拓展（7 独立 API 模块注册） | P0 | 拓展兼容能力 |
| 兼容性 | 兼容主流服务器系统与浏览器；4K 大屏（整屏 ≥3840×2160） | P1 | 软硬件适配 |
| 可维护性 | 结构清晰、注释完整、文档齐全，便于运维升级 | P1 | 可维护性需求 |
| 可用性 | 无单点故障，核心流程降级可用 | P1 | 隐含 |

### 边界与异常
- 空状态：楼栋/子系统无数据 → 显示"暂无数据"占位与引导，不崩溃。
- 错误状态：接口失败 → 模拟数据兜底或明确错误提示（遵循 openapi.yaml 错误码），不白屏。
- 加载状态：模型/数据加载中 → 显示项目真实加载文案（如"正在加载开平市中心医院能源数据…"），禁用"Welcome to/Lorem ipsum"。
- 权限拒绝：低权限操作高危控制 → 拦截并提示。
- 离线/弱网：WS 断开 → 实时降级为最近缓存并提示"实时连接已断开"，恢复后自动重连。
- 并发：多用户同时控制同一设备 → 以最后指令为准并 WS 广播状态，防冲突。
- 1 号楼待台账：设备级视图显示"待台账，现场调研补充中"，不展示占位假数据。

## 12. 数据埋点方案（MVP 必埋）

|----------|----------|------|

  4. 真实硬件协议细节（Modbus 寄存器表/MQTT 主题）待甲方设备到货后对接；以 ADR-003 + openapi.yaml 为边界。
  5. **契约漂移风险（新增）**：openapi.yaml 为前后端唯一契约，PRD 字段/错误码须保持一致；任一端变更须同步 PRD 与 openapi.yaml，建议纳入变更评审。
- **结论**：PRD v1.1 已与架构数据模型（buildings×subsystems×devices）及 API 契约（7 模块 + 跨域 + WS，openapi.yaml）对齐，可作为 Phase 1 前后端联调依据；建议主理人推动甲方补全合同延迟量化指标（R2），并安排架构师/设计师对齐"混合数据层(ADR-003)"与"双联动顶部菜单"两项关键设计后启动编码。
