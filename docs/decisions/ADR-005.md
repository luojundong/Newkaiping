# ADR-005: 后端框架选型 — NestJS（Fastify 平台）+ TypeScript

- 状态：Accepted（2026-08-17）
- 决策者：高见远（首席架构师）

## Background
需承载：REST API + WebSocket 实时推送 + 多协议数据接入（MQTT/Modbus/HTTP）+ 告警引擎 + 控制指令服务 + RBAC。团队以前端（Vue/TS）为主，期望前后端类型贯通、模块化清晰（7 子系统对应 7 模块）。

## Decision
采用 **NestJS ^11（Fastify 平台）+ TypeScript**：

- 模块化：`AuthModule / SceneModule / BuildingModule / DeviceModule / 7 个子系统 Module / AlarmModule / EnergyModule / WsModule / ConnectorModule`。
- 实时：`@nestjs/platform-socket.io`，`WsModule` 按 `building_id/subsystem/device_ids` 订阅推送。
- 接入层：`ConnectorModule` 承载 `ConnectorFactory` 与各 `Connector` 实现（见 ADR-003）。
- 鉴权：`@nestjs/jwt + passport-jwt` + 自定义 RBAC Guard。
- ORM：`@nestjs/typeorm`（见 ADR-004）。

## Consequences
正面：
- TS 前后端贯通，共享类型，减少联调摩擦。
- DI + 模块化与 7 子系统天然映射，扩展性强。
- `mqtt.js / modbus-serial / axios` 生态成熟，Fastify 性能高。

负面：
- NestJS 有一定学习曲线（以结构化收益抵消，团队可接受）。

## Alternatives
- Fastify + TS（手写分层）：更轻但结构约束弱，评分 22 < 23，备选。
- Python FastAPI：与前端主语言不一致，协作成本偏高，评分 21，未采用。
- Go + Gin：性能优但 MVP 开发慢、团队不熟悉，评分 18，未采用。
