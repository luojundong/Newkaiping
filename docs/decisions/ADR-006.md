# ADR-006: 顶部导航联动模型 — 楼栋选择器 + 子系统页签双维联动

- 状态：Accepted（2026-08-17）
- 决策者：高见远（首席架构师）

## Background
需求：「顶部菜单需同时联动楼栋与子系统」。需在大屏顶部用一套导航同时表达「选哪栋楼」与「看哪个子系统」，并驱动中央 3D 场景与左右数据面板整体联动。

## Decision
采用「楼栋选择器 + 子系统页签」双维联动模型：

- 菜单由后端 `menus` 表驱动（动态可配）：第一级「楼栋选择器」（10 栋 + 「全院」），第二级「子系统页签」（7 子系统 + 「综合概览」）。
- 前端 `sceneStore` 持有 `selectedBuilding` + `activeSubsystem` 两个状态。
- 联动契约（任一变化触发）：
  - 3D 场景：飞向 `building_anchors[selectedBuilding]`、高亮该楼、按 `activeSubsystem` 过滤 `device_points` 点位；
  - 左面板：渲染该楼该子系统 KPI + 设备列表；
  - 右面板：调用对应 `/api/v1/{subsystem}/status?building_id=` 渲染子系统视图；
  - 实时：`WS` 订阅参数随双状态重订阅。
- 「综合概览」=`selectedBuilding=全院 & activeSubsystem=overview`，调用 `/regulation/overview` 出全楼聚合。

## Consequences
正面：
- 精确满足「顶部菜单同时联动楼栋与子系统」需求。
- 状态集中（sceneStore），3D/面板/实时三处联动一致，避免状态漂移。
- 菜单后台可配，楼栋/子系统增减无需改前端。

负面：
- 双维状态使联动逻辑较单维复杂（以明确的状态契约与单一数据源控制，风险可控）。

## Alternatives
- 单维菜单（仅子系统）：无法表达楼栋选择，不满足需求，拒绝。
- 楼栋与子系统分属两处独立菜单：联动弱、用户心智成本高，未采用。
