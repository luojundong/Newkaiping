# ADR-004: 数据库选型 — PostgreSQL 16 + TimescaleDB 2.16（单实例双引擎）

- 状态：Accepted（2026-08-17）
- 决策者：高见远（首席架构师）

## Background
合同硬性要求「高性能关系型 + 时序数据库组合」，用于设备时序数据、业务数据（楼栋/设备/用户）的存储、查询、统计分析。部署为医院内网单机（Xeon 8C/64G/1TB+4TB HDD），要求运维简单、可私有化。

## Decision
采用 **单实例 PostgreSQL 16 + TimescaleDB 2.16 扩展**：

- 关系表：`buildings / subsystems / devices / device_points / users / roles / permissions / alarms / alarm_rules / energy_aggregations / connector_configs / scene_configs / feature_flags / operation_logs / menus` 等。
- 时序超表：`device_metrics`（按 `time` 分区，索引 `(device_id, metric_key, time)`）；可选 `energy_readings` 配连续聚合出 hour/day/month。
- 开启 TimescaleDB 压缩（segment by device_id），降低历史存储成本（契合 4TB HDD 历史存储）。
- ORM：`@nestjs/typeorm + typeorm`，超表创建通过自定义 SQL 迁移执行。

## Consequences
正面：
- 单实例同时承载关系与时序，运维只管一个库。
- `time_bucket` / 连续聚合 / 压缩原生支持，能耗与趋势统计高效。
- SQL 统一，开发与排障成本低。

负面：
- 需使用 TimescaleDB 镜像（`timescale/timescaledb:2.16.0-pg16`），部署需带该镜像（私有化内网需预置，已纳入 compose）。
- 超表 DDL 较特殊，迁移需谨慎（有官方工具，可控）。

## Alternatives
- PostgreSQL + InfluxDB（双库）：跨库关联复杂、双份运维，评分 21 < 23，未采用。
- MySQL + InfluxDB：时序能力与 SQL 生态弱于 PG+Timescale，未采用。
